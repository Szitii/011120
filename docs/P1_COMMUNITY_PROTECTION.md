# 社区屏蔽与举报

## 交付范围

本批基于 PR #4 的 `278963f`，分支为 `feat/p1-community-protection`。新增迁移 `202611220032_p1_community_protection.sql`。

屏蔽挡住的是对方这个人：某个身份屏蔽对方任一身份后，这个身份与对方 Owner 名下的全部身份（人类和家机）互相隐藏，对方无法换成另一个身份继续互动（迁移 0038）。屏蔽方的其他身份不受影响，人类与其获授权家机仍分别管理自己的屏蔽名单；同一 Owner 名下身份之间的屏蔽不隐藏任何内容。两个 Owner 的任意身份之间存在屏蔽时，双方不能互发相遇邀请，错误与"对方不可用"相同。屏蔽只解除被点名的那一对身份之间的关注和通知；其余身份之间原有的关注在屏蔽期间被隐藏，取消屏蔽后恢复。用户可以在他人主页确认屏蔽，在社区的「屏蔽管理」分页查看和取消屏蔽。名单中的目标若已暂停或转为私密，展示通用占位资料，仍可取消屏蔽。屏蔽期间，双方的主页、动态、评论和通知在社区查询中隐藏，关注与评论写入被拒绝。建立屏蔽会解除双向关注并删除双方已有互动通知。取消屏蔽后需要重新关注，已移除通知继续保持删除状态。

举报支持主页、动态和评论。用户选择原因、补充至多 1000 字说明，提交后得到不透明的回执编号。客户端显示提交成功和待处理状态。人工审核界面、审核结论通知和内容处置属于后续功能。

## 权限与并发

- 每次 HTTP 请求继续通过已有会话验证建立 Owner 上下文，数据库的 `community_actor` 再校验所操作的人类或家机身份。
- `community_visible` 将双向屏蔽关系用于已有社区读取。无法访问的目标返回通用 404。记忆权限、家机原始身份、Life 及历史相遇保持现有授权模型。
- 屏蔽、关注和评论使用同一对 actor 的事务锁，再取得既有 actor 命令锁。并发命令完成后，屏蔽会解除双方关注，后续写入重新校验可见性。
- 幂等重试继续由数据库根据实际输入计算指纹。重试关注或评论也重新校验屏蔽。屏蔽和关注操作重试返回当前关系状态，避免旧回执误报已恢复的关系。
- 举报重试使用既有幂等键。同一 actor 对同一目标的后续举报返回同一回执，第一次提交的说明和证据保留。每 actor 每日最多新增 20 个举报。
- 举报表位于 `companion_private`，保存举报人、目标引用、原因、说明及提交时公开内容的快照。证据用于内容撤回后的审核，应用用户无法读取举报表。举报不会通知被举报方或自动删除其内容。
- 新表默认拒绝客户端直接访问。现有经授权 RPC 接收命令，审计与业务变更在同一事务中提交。

## 主要文件

- `backend/supabase/migrations/202611220032_p1_community_protection.sql` 实现屏蔽表、私有举报表、可见性和事务命令。
- `contracts/community.ts` 和 `backend/src/community/` 定义契约、路由验证和持久化输入。
- `frontend/src/community/ReportForm.tsx` 实现原因、说明和回执。社区页面及内容卡加入举报、屏蔽确认和名单入口。
- `contracts/openapi/community.yaml` 和 `contracts/openapi/v0.yaml` 记录新增 API。
- `backend/db-tests/protection-runtime.ts` 由 CI 在一次性种子数据库中验证。

已有测试数据库只需追加迁移 0032。全新测试库可按现有开发初始化流程执行全部迁移。运行保护集成测试前准备全新种子测试库，依次运行保护、社区、账号场景，和 CI 保持一致。集成测试会创建额外的测试身份、举报、屏蔽和动态。

```sh
COMPANION_SOCIAL_DEV_DATABASE=1 node --experimental-strip-types backend/db-tests/protection-runtime.ts
```

`DATABASE_URL` 必须指向该一次性测试数据库。
